# 部门共建手册（Department AI Playbook）

> 平台长期成败取决于组织机制，不是代码量。本手册定义部门如何与平台共建 Agent。
> 关键分工一句话：**部门扛「业务真实性 + 应用推广」，平台扛「AI 可实现性 + 能力底座」。**

## 一、五角色职责表

| 角色 | 职责 | 必须避免 |
|---|---|---|
| 平台负责人 | 建设 FLAi-OS 底座、维护方法论与契约、把控架构、组织培训、**拒绝破坏架构的临时需求**（宪法第十条授权） | 变成所有需求的唯一开发者 |
| 部门 AI 应用负责人 | 收集本部门真实痛点、梳理业务流程、提供样例数据、组织专家审核、推动本部门使用 | 只提「我要一个 AI」而不梳理流程 |
| 业务专家 | 定义业务边界、审核结果、标注错误、提供经验知识 | 让大模型自行猜测专业流程 |
| 开发骨干 | 在平台规范（Agent/Tool Package 标准）下参与建设 | 绕过 Registry/Gateway 写私有直连 |
| 使用人员 | 按流程提交任务、使用结果并反馈问题 | 把未经人审的输出当工程结论 |

## 二、Agent 孵化六步 SOP

| 步骤 | 做什么 | 可操作检查项（全过才进下一步） |
|---|---|---|
| 1. 业务流程澄清 | 部门负责人牵头写清现状流程 | □输入是什么 □输出是什么 □谁审核 □耗时环节 □易错环节 □现有工具 □人工判断点 |
| 2. AI 适配性判断 | 平台侧判型 | □归入四型之一：工具自动化 / 知识问答 / 结构化生成 / 推理辅助 □或如实判「暂不适合」并说明原因 |
| 3. Agent 设计卡片 | 双方共写 | □适用范围 □**不适用范围（≥1 条）** □输入/输出 □模型画像 □知识范围 □工具清单 □人工审核节点 □负责人 □测试样例 ≥3 |
| 4. 开发与验证 | 按 docs/02/03 标准开发 | □agent.yaml 过 schema □eval_cases 全绿 □Mock 数据如实标注 |
| 5. 发布上线 | 按 L0→L3 逐级走（准入条件见 docs/02） | □当前级准入条件逐条对勾 □status 与 maturity 如实填写 |
| 6. 运维迭代 | 持续记账 | □用户反馈进 feedback □失败案例沉淀为 eval case □知识/工具/模型变更跑回归 |

## 三、路由四问（新需求进来先过这四问）

1. **落哪类？**——四型之一，还是暂不适合（规则不清/数据拿不到/纯专家判断）？
2. **有没有现成 Agent？**——已有 Agent 扩 eval case / 升版本能不能覆盖？
3. **能不能只加 Agent Package 解决？**——能 → 走六步 SOP，零平台核改动；
4. **装不下才议改平台核**——由平台负责人裁决，写 ADR，绝不为单个需求开后门。

## 四、需求提交模板（部门负责人填）

```text
需求名称：
提出人 / 部门：
现状流程（一段话）：
输入（文件/参数，附脱敏样例）：
期望输出：
现在谁做、耗时多少：
业务审核人（谁为结果签字）：
不适用范围（这个 AI 绝不该做什么）：
样例数据能否提供（脱敏责任在部门）：
```

## 五、同步机制

- **每周更新日志**：新增/修复/试点/问题/下周计划（进 /changelog 页，M2 后）。
- **月度 Demo 会**：新 Agent 演示、优化案例、部门试点汇报、**失败经验**（失败必须上台——沉淀比表扬值钱）。
- **部门 AI 应用负责人小组**：场景收集 → 反馈 → 培训 → 推广的常设闭环。

## 六、红线（对部门侧）

- 样例数据**必须脱敏后**才能出部门；涉密数据的密级判定责任在部门。
- 不得要求平台「先绿起来再说」——Mock/未验证状态如实展示是平台底线（宪法第五条）。
- 不得绕过平台直接找开发骨干写「临时脚本」——那是回到不可维护的老路。
