# N10 真人新手走查协议与逐人记录模板

> **性质**：这是一次真实用户观察协议，不是自动化 E2E、可用性宣称或演示脚本。
> 当前仓库只提供协议和**空白**记录模板；任何参与者、用时、成功率和原话都必须在
> 真人走查现场产生，禁止预填或推测。

## 1. 样本口径

- 目标：先取得至少 **2 位不同真实同事**的首次使用观察（`n >= 2`），再决定下一批
  UI/UX 与重型产品建设。
- 合格参与者：未参与本轮界面设计/实现/验收，且此前没有被逐步教学过本场景；记录其
  岗位类型即可，除非组织流程要求，不在仓库写真实姓名或敏感身份信息。
- 一名开发者自测、审计 Agent、Playwright 运行或同一人重复两次，均不能增加 `n`。
- 可使用明确标注的合成数据，但必须运行真实当前版本；合成数据不等于合成用户。
- 参与者因严重阻塞中止仍是一条有效观察，但必须原样记「中止」；不能改写成完成。
- `n` 统计符合新手口径且留下完整原始记录的真人观察场次，不统计十步成功数；真实
  blocker 导致的中止可计入 `n`，环境准备无效或身份不符合的场次不计入。

## 2. 现场角色与纪律

| 角色 | 可以做 | 不可以做 |
|---|---|---|
| 参与者 | 按自己的理解操作、出声说想法、随时停止 | 为迎合观察者而照预定路径表演 |
| 观察者 | 读任务目标、记时间/点击/原话、在安全或完全阻塞时救援 | 指控件位置、替参与者解释状态、把自己的结论写成参与者原话 |
| 记录人（可与观察者同人） | 使用下方模板逐步留痕，给截图/录屏写受控证据路径 | 在事后凭记忆补造精确用时或引语 |

开始前告知参与者：测试的是产品而不是人；使用合成数据；可随时暂停；若录屏，先取得
明确同意并按内网资料规则存放。观察者除读出每步的**目标**外不讲路径。连续停滞
90 秒或参与者主动求助时可以救援，但该步记为「有帮助完成」，并逐字记下帮助内容。

## 3. 环境准备

- 记录精确 commit/build、浏览器、屏幕尺寸、light/dark 与输入方式；不在走查中途换版本。
- 准备一个普通权限测试账号，不给管理员或隐藏开发入口。
- 准备明确标注为 SYNTHETIC 的会话、可运行任务、`waiting_review` 任务、含至少 4 个
  输出的已签任务；不得混入真实敏感/EAR 数据。
- 清空或记录参与者可见的预存状态，避免个人历史让某一步天然命中。
- 若某前置数据准备失败，记录为环境无效并重约；不能把环境失败算作产品成功或失败。

## 4. N10 十步任务（只读目标，不读操作路径）

每步均记录：首次动作、是否无需帮助完成、用时、停滞点、参与者原话、观察者救援、
最终可观察结果。

| # | 给参与者读出的目标 | 观察重点 |
|---|---|---|
| N1 | 请用自己的话说明这个平台能做什么、不能替你做什么。 | 首屏心智模型；是否误以为模型可判定/签发 |
| N2 | 请发起一个新的工程问题，并判断系统下一步需要你做什么。 | 主会话入口、发送反馈、运行/等待信号是否降低焦虑 |
| N3 | 请根据系统给出的信息创建一个任务，但在提交前核对关键输入。 | 推荐是候选而非自动执行；结构化字段与人工确认是否清楚 |
| N4 | 请找到刚才创建的任务，并说出它现在处于什么状态。 | 会话到任务台的回路；状态色/文字是否被正确理解 |
| N5 | 请判断任务当前由谁/什么处理、是否还在工作，以及你现在应等待还是行动。 | 工作中反馈、断连/停滞误判、缺少动静造成的焦虑 |
| N6 | 请定位观察者给出的一个旧会话、旧消息或任务编号。 | 精确寻址搜索；是否把「无结果」误当系统无数据 |
| N7 | 请查看一项已完成任务的证据、来源与输出，并指出哪些内容已经核验。 | `completed` 不等于 REAL；来源、证据、人工签发的区别 |
| N8 | 请处理一项等待审核的合成任务：选择批准或驳回，并说明理由。 | 人是唯一签发者；决定后果与理由输入是否清楚 |
| N9 | 请找到观察者预先准备的已签合成任务的第 4 个输出并取得它；不要由观察者指出位置。 | 输出折叠、精确 artifact 定位、下载结果；不把预览当发布 |
| N10 | 请说明这份产物下一步会被怎样使用，并提交一条真实反馈。 | 「签发≠用上」的 outcome；下载/下轮引用/未采用的真实去向 |

若当前 build 不具备某一步所需的已声明能力，观察者应在记录中标为「版本不具备」，
不得临时换成未来设计原型，也不得给产品记成功。

## 6. 两人完成后的收口方式

只有完成至少两份合格的逐人原始记录后，才能另建聚合报告。聚合时：

1. 先列共性问题和相反证据，再给建议；单个响亮意见不能冒充共识。
2. 将每个问题链接回参与者编号、步骤和原始证据，不暴露不必要身份。
3. 区分「阻塞」「焦虑/无反馈」「误解信任状态」「偏好」与「环境故障」。
4. 给每条建议写最小可证伪验收条件；不得先决定 UI 解法再选择性引用观察。
5. `n >= 2` 只解锁基于信号的下一轮设计，不证明产品已达到统计显著或生产可用。
