# ADR-0060：建立需求信号、路线图承诺和工程 Issue 分层的需求共创闭环

- 状态：产品方向已接受（委托人在本次设计会话中确认，2026-07-23；不构成组织签发、试点或上线授权）
- 关联：ADR-0052、ADR-0057、ADR-0058、ADR-0059

FLAi-OS 的工程师和业务人员不仅是使用者，也是核心需求提出者。平台建立低门槛、可追踪的需求共创闭环，使真实痛点能够被看见、聚合、筛选、正式采纳并最终回到能力发布与验证结果；共建地图不再只由平台开发者闭门规划。

用户提交时只需提供一段自然语言，可选关联任务、会话、文件、截图或其他证据，不要求填写复杂 PRD。认证身份、提交时间、来源类型和可获得的任务上下文由平台自动绑定。需求信号可以来自主动建议、任务反馈、失败任务、会议决定、审计发现、重复人工操作或经权威知识底座确认的领导正式指令；各来源保持可区分，普通意见不能冒充权威命令。

AI 可以对需求信号做预处理：提取痛点、场景、期望结果和候选验收标准，识别相似项，建议聚类与分类，提示可能缺失的证据、依赖、密级和安全影响。所有 AI 推断都是草稿，必须与原始文字分开保存；AI 不得决定采纳、拒绝、优先级、负责人、路线图状态或工程排期，也不得自行把需求写入权威知识层。

人工筛选分别查看安全与合规紧迫性、痛点严重程度、发生频率、受影响范围、时间与质量影响、战略一致性、证据充分度、实施依赖和成本，不压成一个不透明总分。“我也遇到”只增加独立需求信号和覆盖证据，不是投票晋级机制；热门但低价值的建议不能自动挤过小众但高安全风险的问题。

需求信号具有不可变原始记录和追加式事件历史。相似需求可以合并到同一候选项，但必须保留每条原始信号、提出者、时间、证据和关联关系；不得用合并删除来源或把最早提出者替换成整理人员。用户可选择是否在团队视图展示姓名，授权治理角色仍可读取真实认证来源。需求及附件继承原始任务和文件密级，敏感内容只能在相应角色范围内展示；共建地图需要时使用脱敏摘要或受限节点。

用户可见的生命周期至少覆盖：已收到、已合并或待补证据、候选池、已采纳、已规划、开发中、验证中、已发布，以及暂缓或不采纳。每次状态变化记录具名操作者、时间、理由和相关证据；暂缓、不采纳、合并与拆分也必须向提出者回告，不能让需求进入无回应的意见箱。缺少必要信息时采用异步、聚合的补充请求，不在用户正常 Agent 工作中反复插入表单。

需求信号、路线图承诺和工程 Issue 是三个不同事实层：

1. 平台需求池保存产品发现事实和完整来源；
2. 版本化 FLAi 共建地图保存经过授权人员正式采纳的路线图承诺；
3. GitHub Issue 或经批准的内网工程追踪器保存交付执行事实。

原始需求不会自动成为路线图节点或工程任务。正式采纳时创建或关联共建地图节点并写明决策理由、来源需求和预期验收；只有获得路线图承诺后，具名人员才能创建工程 Issue，并把 issue、能力发布包和 FLAi Bench 证据回链到原需求。三层通过稳定引用互相连接，但不复制和争夺彼此状态。

共建地图可以展示“该目标来自多少条真实需求、涉及哪些场景和证据”，但不得泄露受限内容或把提出数量直接解释成优先级。正式进入试点或验收时，应邀请原提出者或同类需求代表自愿参加，发布后回告对应版本、验证范围、已解决部分和仍未解决边界；关闭需求必须有可回查结果，不以代码合并本身冒充用户问题已解决。

本 ADR 决定需求发现与追踪机制，不指定最终采纳角色矩阵，也不授权当前混合工作树上的表结构、API、通知连接器或 GitHub 写操作。实施前必须进一步固定决策权、需求与事件合同、合并/拆分语义、密级与可见性、异步回告机制、路线图和 issue 引用合同，以及至少覆盖 AI 自批、点赞自动晋级、合并丢来源、敏感需求泄露、无理由关闭和未采纳自动建 issue 的 invalid-first fixtures。
