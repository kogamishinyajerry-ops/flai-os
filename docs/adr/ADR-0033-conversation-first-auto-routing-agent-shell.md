# ADR-0033：会话优先的自动路由 Agent Shell

- 状态：Accepted（2026-08-01）
- 关联：ADR-0012（interactive 会话运行时）· ADR-0014（会话附件）· ADR-0016（协作编排）· ADR-0031（Agent Shell 本体投影）
- 替代范围：在**工程师侧交互**上，本 ADR 取代上述 ADR 中“选择 Agent、逐字段补全、跳转创建页、常驻上下文轨道”等旧口径；底层运行时、确定性校验、本体投影与人工签发边界继续有效。

## 背景

Agent、模型、工具、Workflow、输入 schema 与资产分类是平台内部的编排语言，不是
工程师完成工作的前置知识。把这些结构暴露成选择器、参数表单或 JSON 编辑器，会把
本应由系统承担的理解与路由成本转嫁给工程师，并分散对当前任务的注意力。

## 决策

工程师工作台采用**一个主任务、一个主输入**。工程师提供原始意图只有两种方式：

1. 输入自然语言；
2. 上传附件。

其余交互只能是对系统已形成方案或治理节点执行清晰的按钮动作。工程师壳不得出现
要求用户填写参数、编辑 JSON、选择分类、选择模型、选择工具、选择 Workflow 或选择
Agent 的控件，也不得用多块常驻面板变相恢复这些选择。

系统根据对话、附件、Agent Package、本体投影、Registry、工具白名单、知识范围与
输入输出契约，自动完成 Agent、模型、工具和 Workflow 路由。所需信息不足时，系统在
同一对话中用自然语言追问；不得把用户送去字段表单补空。路由结论先以人话摘要呈现，
路由依据、边界、拟使用的 Agent/工具等内部上下文只通过只读的按需披露展示，不得在
披露区提供改选或参数编辑能力。

对话型垂类能力同样由统一入口自动路由。匹配制度/标准问答时，Guide 可在同一会话
内部转交给已审定的 interactive 专家，最终只展示目标专家经过自身依据契约校验的
回答；工程师不选择 Agent、不跳转新会话，也不创建任务。ConversationService 必须
在同一不可变 Registry 代际内复核目标包、interactive mode、下线状态、附件密级和
模型调用归因。当前服务尚未携带 actor role，因此自动转交面暂以审定 allowlist 收口；
角色化授权进入运行时前，不得泛化到任意 interactive Agent。

自动路由不改变治理边界。人保留并必须明确触发以下门：

- 开工确认；
- 影响工程判断的关键决策确认；
- 结果签发。

人确认的是任务目标、方案、证据与责任，而不是手工编排平台组件。LLM 仍只提出建议；
Agent、工具、schema、权限与安全门继续由确定性代码校验，人仍是唯一签发者。

## 编排与附件边界

- **单 Agent 方案**：系统可从对话与附件自动整理执行输入并形成完整计划；通过确定性
  校验后，仅向人呈现一次“按方案开工”确认，不再跳转到创建任务表单。
- **多 Agent 方案**：只有整份计划达到可执行条件时才允许开工，不以“先执行已就绪
  子集”制造部分成功。任一 Agent 因非法、下线、重复、超出上限或其他原因被剔除/截断，
  整份计划立即回到同一对话重新编排；不得保留剩余 Agent 并开放“残缺方案”开工。前端
  对 `dropped_agents`、`capped`、`truncated` 等信号继续设置防御性关门。
- **多 Agent 附件归属不明确**：系统不得猜测、不得默认把全部附件共享给所有 Agent，
  也不得退回附件分配表单；必须 fail-closed 回到同一对话，追问到归属可确定或方案被
  重新编排。
- **附件确定性记账**：服务端先从整个当前工作段生成稳定的“附件 1 / 附件 2”名册，
  模型只能用这些标签提出用途；Workflow 必须把每份附件恰好解析为某个 Agent 的
  `{file_id, filename}`，或显式记为本轮忽略。未知标签、重复绑定、漏记账、`none`
  模式带附件、`file_upload` 数量或后缀不符都返回自然语言追问，不把内部 id 或分配表
  暴露给工程师。同名文件依靠稳定标签区分，不依靠文件名猜测。
- **同一文件能力匹配到多份历史附件**：在方案尚未携带确定性附件血缘前，不得按后缀
  把多份文件全量转发；只有恰好一份匹配材料时才可开工，其余情况 fail-closed。
- **工作段隔离**：同一会话可连续承载多项工作。最近一次任务创建、Guide 明确拒绝、
  canonical 制度/标准问答交付三者的最新时点共同构成工作段终点；后续方案只能携带该
  时点之后、已由服务端保存的用户附件。附件名册与密级判定必须在 LLM 正文截窗之前，
  基于完整当前工作段计算，不能因对话超过 40 条而遗失仍有效材料。历史任务快照尚未
  加载时不得短暂开放开工，batch 成功到 live feed 刷新之间由响应时间戳先行划界。
- **仅附件输入**：只要存在有效附件，空文本消息也是合法工程师输入；系统应从附件
  开始理解并在需要时追问。

失败恢复同样属于受控编排：`retry_of` 只能指向真实存在且状态为 `failed` 的旧任务；
任意 URL 参数不得把 queued/completed 等任务伪装成“重跑自”审计血缘。前端必须先
读取权威任务再启用恢复语义，模型在飞期间钉死提交时的恢复来源；batch 成功后先关闭
重复开工门，再独立清理 URL，导航清理失败不得谎报任务未创建。
首次重试创建新会话并写入 `c` 时，前端必须使用一次性内部路由绑定标记消费该次 URL
同步；不得触发常规会话 reload 清空乐观用户消息或附件。该标记只覆盖本次内部导航，
不能屏蔽用户主动切换会话。内部镜像命中时仍须递增 route/retry epoch，使此前外部导航
发出的迟到读取失效；上传、建会、URL 镜像与消息提交前后都复核同一个 retry 快照。

## 代际钉扎、原子创建与恢复

人工点击“按方案开工”时，前端必须重新读取每个 Agent 的不可变 Package Snapshot，
同时钉住版本号与内容摘要。batch API 在任何任务写入前，从同一 Snapshot 同时复核
manifest、输入 schema、版本与摘要；运行时在加载 Workflow、工具或注册输出之前再次
核对任务元数据中的摘要。相同版本号但包内容已变化同样 fail-closed，不能只比较版本。

每次 batch 使用 128-bit CSPRNG 生成的 `operation_id`，任务 id 与请求指纹由该操作
确定性派生。前端在发出 POST 前先把会话、原操作号、完整请求、版本与摘要写入可刷新
恢复的会话级操作日志；日志无法写入时不得请求，日志损坏时不得换 key 重建。重放同一
请求只返回原任务；相同操作号配不同内容返回
`batch_operation_conflict`。前端只有在 2xx 响应的操作号、任务数量、顺序、会话、
Agent、依赖、retry 血缘、版本和摘要全部与请求一致后，才进入成功态。网络中断、5xx、
畸形 2xx 或幂等冲突一律保留“落库状态未知”锁与原 `operation_id`，由显式对账动作恢复；
`conversation_not_active` 表示权威零写入，可解锁并引导新对话，不得与未知落库混同。

## 兼容与退役

`/tasks/new` 的 URL 仅保留为兼容重定向：旧书签、通知或手工输入都会丢弃 Agent 与
参数 query，回到主对话；它不再加载任务创建表单。Guide、Portal、快捷切换器、任务台、
失败重试与协作工作台都不得把工程师导向字段式创建页。存量 `TaskCreate` 源码暂留以便
审计旧行为与后续安全删除，但已不属于可达产品 Surface，也不得重新接回导航。
旧的字段式资产整理抽屉同样退出正式 Guide Surface，仅可作为开发验收档案保留；资产
沉淀重新接入时必须由系统先从对话与证据自动归纳，缺口仍在同一主输入自然追问，不能
以分步问卷或第二组输入控件回归。

## 后果

工程师只需描述问题、提供资料并在责任节点作决定，平台内部的本体与编排能力转化为
自动路由资产，而不是新的学习负担。代价是系统必须维护可解释的路由、对话式缺失信息
闭环与严格的 fail-closed 语义；任何新增领域能力都应先接入这些通用契约，而不是新增
一组领域专用表单。
