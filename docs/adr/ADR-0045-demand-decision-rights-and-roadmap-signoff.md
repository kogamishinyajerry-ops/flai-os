# ADR-0045：需求决策采用策展、领域与安全评审、路线图签发的轻量职责分离

- 状态：产品方向已接受（委托人在本次设计会话中确认，2026-07-23；不构成组织签发、试点或上线授权）
- 关联：ADR-0019、ADR-0029、ADR-0036、ADR-0044

需求共创必须同时满足广泛参与和清晰责任。FLAi-OS 不允许任何原始需求、AI 建议或投票结果自动改变路线图，也不把全部决策能力笼统授予现有全局管理员。平台采用按职责与作用域授权的轻量机制：所有认证试点用户都可提出和补充需求，需求策展人负责整理，适用的领域与安全评审人负责专业门，路线图负责人对路线图版本作最终具名签发。

需求提出者可以提交、补充证据、关联同类需求、表示“我也遇到”、关注状态并自愿参加试用验收；这些行为增加来源与覆盖证据，但不直接授予优先级或路线图修改权。需求提出者可以选择是否在团队视图公开姓名，平台仍以认证身份保留审计来源。

需求策展人在明确的领域、部门或工作流范围内去重、合并、拆分、分类、脱敏、请求补充证据并形成候选摘要。策展动作必须保留原始需求和关系，不能改写用户原话冒充来源。策展人可以对重复、无效输入或明显不在范围内的信号提出处理建议并记录理由，但无权把候选正式采纳进路线图，也不能通过担任全局管理员绕过这一分离。

当需求涉及 CFD、法规、性能、控制、结构或其他专业工程口径时，必须有对应具名领域评审记录，说明痛点是否成立、验收标准是否可用和主要未知项。当需求触及权限、Sandbox、网络外联、敏感数据、知识发布、审计或破坏性动作时，必须触发安全评审门；缺少适用评审、评审证据不可解析或安全门为 false 时，不得正式采纳或进入交付。领域评审提供专业结论，安全评审可阻断不安全路径，但二者不替代路线图优先级决策。

路线图负责人是对某一版本共建地图具有签发权的具名人类职责。它可以正式采纳、暂缓或不采纳候选，必须记录决策理由、来源需求、适用评审、目标里程碑和预期验收；不能豁免安全门、伪造领域意见或让 AI 代签。路线图变化产生新版本与变更记录，不原位覆盖历史承诺。

经权威知识底座确认的领导正式指令以“权威指令来源”进入需求池，并在路线图决策时按其组织效力处理；它仍不能绕过安全控制、实现可行性说明、FLAi Bench 或最终人签。普通会议笔记和转述不能冒充领导正式指令。

路线图承诺形成后，由交付负责人创建或关联工程 Issue，负责实现、版本和证据回链。交付负责人不能以代码合并、任务完成或自测通过自行宣布用户问题已解决；关闭需求至少要关联已发布能力范围、适用的 FLAi Bench 证据和具名验收或明确的剩余边界。原需求提出者或同类代表应被优先邀请参加试用与验收，但不被强迫承担签发责任。

AI 只能预处理、发现重复、提出候选分类和协助起草决策说明；点赞数、需求数量、模型评分和综合优先级分都没有签发权。每次合并、拆分、补证据、采纳、暂缓、不采纳、创建 Issue、进入验证和关闭都生成追加式事件，记录认证操作者、职责、作用域、时间、理由和证据引用，并向受影响提出者回告。

这些职责不预设必须新增固定的全局用户角色枚举。实施时应优先通过单一 policy seam 表达作用域授权和适用门，并在提交和事务提交时重新核对当前身份与权限；角色变更、职责撤销和版本签发必须 fail-closed。当前 `admin|agent_developer|business_user` 等粗粒度角色可以承载试点近似，但不能被文档冒充为最终需求治理模型。

本 ADR 决定决策权和职责分离，不授权当前混合工作树上的角色枚举、数据库、API、通知或 GitHub 写操作。实施前必须固定职责委派与作用域合同、适用领域/安全门判定、路线图签发事务、关闭验收合同、回告机制，以及至少覆盖策展人自批、管理员越权、缺领域评审、缺安全评审、AI 代签、交付人自验关闭和权限提交时漂移的 invalid-first fixtures。
