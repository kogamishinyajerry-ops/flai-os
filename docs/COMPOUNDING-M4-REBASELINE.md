# FLAi-OS 复利结构重排：M4 前后开发纪律

> **状态**：2026-07-19 owner 方向裁决的仓库化基线。
>
> **中心诊断**：V0.1 在封板声明范围内证明了既有信任机制与 job 数值类生长骨架，
> 但这不覆盖目标机、真实业务采用或长期运行，也尚未证明「这台机器越用越聪明」。
> 当前短板不是继续增加同类信任机制，而是让每次真人工作留下可供下一次复用的判断、
> 课题、对账与使用结果。
>
> 本文只重排开发顺序，不降低既有治理门：**人是唯一签发者**、fail-closed、
> 声明不超过证据、候选生成/人工批准/精确发布三态分离，全部继续有效。

## 1. 立即生效的排序裁决

### 1.1 2026-07-20 owner 排序例外：延期 N10，继续本地可信收口

Owner 已明确要求“先跳过真实用户反馈，完成其余收口”。本例外只改变开发顺序，
不改写证据事实：N10 仍为 `n=0`、未执行、未通过，M4 完成谓词与 Gate 1 也仍分别
保持未验证。本例外授权 P2.5–P2.8 继续完成可由本地合同、SQLite 约束、无效输入测试、
浏览器验收和默认关闭接缝机械证明的部分；它不授权把 fixture、开发者自测或本机 daemon
冒充真人反馈、内网采用或生产激活。

因此下面的“双门后再做重型产品建设”仍是默认政策，但本次 owner 例外允许按窄切片
提前完成实现准备。凡依赖真实组织关系、目标机、生产凭据、真实 daemon 部署或发布 owner
裁决的结论，必须停在 default-off/未配置/待批准状态；不得因为代码和测试完成而写成
N10、M4、Windows 离线交付或生产发布已通过。

P2.4 精确寻址搜索完成浏览器验收后，**冻结 P2.5–P2.8**。冻结不是删除需求，
而是不再用真实用户信号缺席时的主观判断继续扩写 UI、收件箱、会话生命周期或
Open Design 生产资产流水线。

重型产品建设的排期解锁必须同时满足：

1. **N10 真人新手走查 `n >= 2`**：至少两位不同的真实同事按
   `docs/N10-NOVICE-WALKTHROUGH.md` 独立参加协议并留下完整逐人原始记录。`n` 统计
   合格真人观察场次，不要求十步成功；若因真实 blocker 中止，按协议原样记中止而
   不是粉饰成完成。受控的结构化记录包须通过
   `scripts/verify_n10_observation_package.sh/.ps1`；该 exit 0 只表示申报记录完整且
   申报的去重合格场次至少 2 条。报告必须明示
   `N10_DECLARED_RECORD_PACKAGE_STRUCTURALLY_COMPLETE=true`、
   `owner_identity_confirmation_required=true`、`roadmap_effect="none"` 与
   `m4_status="not_evaluated"`。排期 owner 仍须核对 exact 摘要、受控原始记录与
   身份对照，确认是两位不同真实同事；自动化 E2E、开发者自测、审计员评语都不能
   充当真人样本。
2. **M4 信号包完成谓词为 True**：严格按
   `docs/M4_intranet_day1_recon_checklist.md` 的「M4 信号包完成谓词」逐项判定。
   已取证的负结果可以进入信号包并触发安全补偿；空白、`unknown`、未跑探针、缺少
   必需的 policy owner 或证据路径，一律 fail-closed，不解锁。现场证据回收后须通过
   `scripts/verify_m4_signal_package.sh/.ps1` 对 exact package/evidence 摘要机械复算；该命令
   只证明 M4 这一半排期门，不证明 N10 或 Gate 1。

这是一道**开发排期门**，不是导入授权门。不可逆内网导入仍须独立通过
`docs/PRODUCTION-READINESS-PROGRAM.md` 的 Gate 1 与具名 owner 终裁。
两个检查器互不代替，也不存在联动自动解锁：只有 N10 的人工真实性确认、N10 结构
完整性检查与 M4 完成谓词均到位后，排期 owner 才可作出解冻决定。

## 2. M4 前的产品功能建设只允许三类工作

本节约束**产品功能建设**，不冻结生产准入本身。Gate 1 的 B1/B3 目标机闭合、生产
阻断缺陷、安全修复、必要回归与证据复核继续优先执行，不计作新产品能力。

| 类别 | 允许的最小落点 | 明确不做 |
|---|---|---|
| 判断采集 | 结构化驳回理由；R0 顾问疑点与人的最终裁决同任务留痕；只记录，不让模型进入判决链 | 自动批准、LLM 代签、以一致率直接触发放权 |
| 真人走查 | 跑 N10、在仓库外受控保留原始观察/媒体、用结构包机械检查完整性、把阻塞/焦虑点转成可复现实验输入 | 将真实样本或媒体提交进仓库；用开发者自测或自动化脚本填充 `n`；把检查器 exit 0 当成身份/可用性证明；在首批观察前继续凭感觉抛光 UI |
| M4 侦察与叙事 | 索取真实样例、评审关系、第二模型家族、环境证据；维护阶段表/转捩点/关卡等低成本汇报材料 | 课题空间回流/跨会话内核、评审梯子 R1+、新的大型交互面 |

判断采集是**仪器**，不是新的判决者。机器意见必须标明模型/版本、产生时间、疑点
清单与证据指针；人的决定必须保存具名主体、动作、结构化理由与时间。两者可以对账，
但机器记录永远不能改写、替代或预填人的最终签发。

## 3. 第一轮真实信号要回答什么

M4 与 N10 的目的不是为既定方案背书，而是让以下未知量首次可测：

- 哪些类别真的产生高频签发/驳回，人的「为什么」集中在哪里；
- 谁实际审核谁、哪些类别需要什么资格，是否存在同人创建同人签发等职责冲突；
- 内网是否存在第二模型家族；若只有 GLM 同源家族，评审员独立性假设下降多少；
- 用户能否找到下一步、看懂运行/等待/失败/人签状态，以及何处出现无反馈焦虑；
- 签发后的产物是否被下载、被下一轮任务引用或被业务采用，而不是只统计「已签发」。

任何派生指标都必须能回到原始记录。尤其「人机一致率」只说明意见是否一致，不说明
机器意见正确，也不能单独作为 R2/R3 放权依据。

## 4. Post-M4 规格入口：课题空间三相

以下只登记 **post-M4 spec 入口**；M4 前不建表、不迁移、不放宽依赖边界。

### Phase T1：容器相（纯加法）

- 候选形态：`topics` 容器，conversation/task 仅挂可空 `topic_id`，课题页按时间线聚合；
- 零行为变更：不改变签发、知识作用域、数据分级或跨会话依赖；
- 开工前置：至少一条真实、持续多轮的课题样本，先证明字段和时间线来自真实工作。

### Phase T2：回流相（治理性写回）

- 只允许**已由人签发**的产物与判例候选进入课题级 knowledge scope；
- 密级继承、provenance 绑定、撤回/失效语义和读取授权必须先写 spec；
- 候选生成、具名人工批准、正式发布继续是三个独立状态，写回不得偷渡成发布。

### Phase T3：跨会话管道相（内核改动）

- 依赖作用域才从 `conversation` 候选放宽到同一 `topic`，不同 topic 仍 422；
- 沿用 K1 已签发见证闸、`origin=user` 隔离、分级合成、精确产物成员关系；
- 必须独立 ADR/spec、迁移与回滚方案、无授权/跨 topic/未签发输入的负例、tamper
  咬合和异源安全审。任一条件不清楚即 fail-closed，保持现有跨 conversation 拒绝。

## 5. Post-M4 规格入口：评审梯子 R0–R3

R0 的「顾问疑点 + 人裁决」配对记账属于 M4 前仪器；以下登记的是梯子运行政策入口，
不在 M4 前实现 R1+。**LLM 在所有级别都只提供顾问输入，不能直接阻断、批准、签发或
发布**；能关门的只能是独立、可复算且经 owner 批准的确定性政策。

| 级别 | 候选能力 | 硬前置与不可越过边界 |
|---|---|---|
| R0 顾问 | LLM 给出结构化疑点，人作最终裁决并形成对账账本 | 模型不关门、不签发；记录模型家族/版本和原始疑点 |
| R1 确定性关门 | 独立可复算规则可阻止明显不合格候选进入人工队列 | 角色轴、类别权限、确定性核验和真实 R0 对账先到位；LLM 疑点本身不是关门谓词，人仍是唯一签发者 |
| R2 抽检政策 | 对顾问质量和附加复核形成有地板的抽检候选政策 | 必须有真实评审关系、异源性判断和具名 owner 批准；当前每份正式产物仍须具名人工签发 |
| R3 考核放权 | 按持续考核结果调整顾问覆盖范围与附加复核强度 | 可撤回、可审计、漂移触发回退；本文件不授权任何免人签或自动发布路径 |

三个硬前置焊死：

1. **角色轴前置**：先采真实「谁审谁、审什么类别、谁能最终签发」，再设计角色，
   不用抽象 username 猜组织关系。
2. **异源性前置**：确认是否有第二模型家族；若没有，政策必须显式标同源盲区，
   提高确定性核验权重与人工抽检地板。
3. **永久人签地板**：当前宪法下所有正式产物都由具名人签发；其中 `sensitive` 与
   EAR 相邻类别的 **100% 具名人工签发**还须放入未来政策模板不可配置区，任何指标、
   成本压力或成熟度晋升都不能覆盖。未来若想改变其他类别的人签义务，必须另立宪法级
   ADR 并由具名 owner 裁决；本文没有提供这种授权。
