# 10 AI 转型共建执行手册

> 文档状态：`ACCEPTED-NOT-IMPLEMENTED`
>
> 本手册把需求发现、POC、Phase 0A、Phase 0B、推广、复盘与退役串成一套可执行方法。它扩展现行 [部门共建手册](../../08_Department_AI_Playbook.md)，不在本阶段替换其代码或流程事实。需求决策权以 [ADR-0060](../../adr/ADR-0060-demand-co-creation-loop.md) 和 [ADR-0061](../../adr/ADR-0061-demand-decision-rights-and-roadmap-signoff.md) 为准；唯一日常运营入口以 [ADR-0062](../../adr/ADR-0062-feishu-single-organizational-hub.md) 为准。

## 1. 方法论目标

FLAi-OS 的转型不是“把更多流程交给大模型”，而是让组织持续把真实痛点转化为有范围、有依据、有安全控制、有评测和有人负责的能力发布包。每一轮共建都应回答：

- 解决了谁的哪项具体工作结果；
- 哪些事实来自权威知识，哪些是工程师确认假设，哪些只是模型建议；
- 允许自动执行什么，哪些不可逆影响只能进入末端 Delivery Bundle；
- 由什么证据证明能力可用，失败时如何停止、恢复或退出；
- 发布后用户问题解决到哪一部分，还有什么明确边界。

本手册不建设人员绩效系统。Token、任务数、Agent 使用频率和需求数量只用于版本化声明的容量、安全、产品改进和经批准的组织价值分析，不能用于个人排名、考核或“AI 使用积极性”判断。每项指标必须冻结最小聚合粒度、具名下钻职责与目的、保留期、允许投影和导出策略；小样本抑制与深链重鉴权是机械门，不是展示偏好。

## 2. 一条端到端共建路径

| 阶段 | 最小输入 | 核心动作 | 必须产物 | 退出条件 | 立即停止或退回条件 |
|---|---|---|---|---|---|
| 0. 发现 | 一段自然语言痛点，可选任务/文件/截图 | 自动绑定身份与上下文；AI 提取候选场景 | 不可变需求信号 | 来源、密级、痛点和期望结果可识别 | 敏感内容无法安全收容 |
| 1. 策展 | 新信号与相似项 | 人类去重、合并/拆分、脱敏、异步补证据 | 候选项及完整来源关系 | 原始信号不丢失，关键证据可审查 | 只剩模型臆测或无真实用户场景 |
| 2. 路线图决策 | 候选、影响、依赖、适用评审 | 领域/安全评审；路线图负责人具名决定 | 版本化路线图承诺或有理由的暂缓/不采纳 | 理由、里程碑、验收和责任明确 | 缺适用安全门或评审证据不可解析 |
| 3. Outcome Contract | 已采纳承诺、代表性样本、权威依据 | 定义用户结果、边界、证据、停止条件 | 一页结果合同与 tracer bullet | 正常/失败/越权例均可观察 | 无法定义结果或必须依赖未确认事实 |
| 4. POC | 最小合同、approved synthetic 数据；正常样本 `fixture_class=canonical` | 验证最危险技术假设；允许丢弃实现 | POC 记录、失败与结论 | 关键假设有证据，可决定继续/改变/停止 | 只有演示效果，无真实 seam 或证据链 |
| 5. 构建 | 已批准 tracer bullet | 按 Package 标准接入控制内核 | Release Manifest 草稿、测试与限制 | 依赖可版本化，invalid-first 用例就绪 | 需要绕过 Gateway/Registry/Sandbox/Task Event |
| 6. 冻结评测 | 完整 Manifest 与批准用例 | 冻结能力发布包，运行四轨 FLAi Bench | digest、证据矩阵、人工 rubric、门结果 | 必测门 true，无 failed/invalid/skipped/unknown | 外部活态影响结论且不可重建 |
| 7. Phase 0A | 合格冻结包 | 5–8 名技术验收者仅在 approved synthetic 数据上试用；正常样本 `fixture_class=canonical` | 机制验收、事故/恢复、限制和签发记录 | 安全、证据、自治体验和末端交付门通过 | 越权、泄露、无法强杀、审计断链或假绿 |
| 8. R6 真实工作流验证 | Phase 0A 通过；最小真实样本/工具路径与 Owner 获批 | 具名验证人员走一条精确真实路径，领域/安全独立验收 | 真实路径证据包、分类传播、准确性、回退和支持结论 | 可形成 Phase 0B eligible decision；不自动扩大人群 | 真实数据边界不清、回退失败或必须借 synthetic 结论补洞 |
| 9. Phase 0B | R6 通过且精确暴露范围获签 | 20–30 名业务用户限范围试用 | 业务质量、采用性、支持、价值基线和回退证据 | 适用业务 rubric 与生产准备门具备 | 需扩大权限或隐藏限制才能让流程成立 |
| 10. 发布推广 | 具名发布签发 | 分批开放、培训、支持、观察 | 发布 receipt、范围、手册、回退目标 | 用户能完成目标并理解限制/证据 | 失败率或支持负担超出签发范围 |
| 11. 复盘迭代 | 任务、反馈、失败、安全与价值事实 | 回链需求、沉淀 Bench case、决定新版本/暂停/退役 | 复盘记录与路线图更新 | 每个问题有处理结论和证据去向 | 用宣传指标掩盖失败或无基线报价值 |
| 12. 退役 | 风险、低价值、替代或维护结论 | 停止新任务、通知、迁移与归档 | 退役签发、替代关系、保留证据 | 无新入口，历史可重建，用户已回告 | 仍有未识别依赖或进行中正式任务 |

`已采纳` 只表示路线图事实成立，不表示实现、评测或发布已经完成。

目标态中，上述 0～12 阶段都由飞书 FLAi 工作空间承接组织入口、工作收件箱、编排与回告，
但专业操作仍进入对应权威 Surface：GitHub 原生完成代码 diff review、PR approval 与 merge，
FLAi 专业工作台完成受控执行，Knowledge Authority 和安全生存通道守住各自边界。当前
Phase 0A 不接真实飞书；只有 ADR-0062 对应 F 段另获授权并验收后，才可把该段真实能力纳入
运营。飞书投影绑定 owner/version/digest/freshness 和适用的 source evidence；只有治理变迁
才要求 owner receipt。

Stage A～D、R0～R8、Phase 0A/0B 与 F0～F5 的目的和依赖以
[06_Roadmap.md §4.1](06_Roadmap.md#41-四条正交阶段轴) 为准；任一轴完成都不自动推进另一轴。

## 3. 需求发现：让每个人参与，但不把意见箱变成路线图

### 3.1 低门槛入口

用户只需在飞书工作收件箱描述“我现在怎么做、哪里最痛、希望得到什么结果”，平台通过受信 channel 和内部 ActorBinding 自动绑定认证身份、时间、来源和可获得的任务上下文。可选关联任务、失败、文件、截图、会议决定或审计发现，不要求先填 PRD。

AI 可以生成结构化草稿：场景、痛点、候选结果、可能依赖、密级和安全提醒。原文与 AI 草稿必须分开保存；AI 输出不能覆盖原文，也不能自动采纳、排期或建 Issue。

### 3.2 人工筛选

策展时分别看安全/合规紧迫性、严重度、频率、覆盖人群、时间/质量影响、战略一致性、证据、依赖和成本，不压成黑箱总分。“我也遇到”增加独立信号，不授予优先级。合并和拆分保留每位提出者与全部证据。

涉及专业工程口径必须有领域评审；涉及身份、权限、Sandbox、外联、密级、知识发布、审计或破坏性动作必须有安全评审。路线图负责人只在适用门可解析后作具名采纳、暂缓或不采纳，并向提出者回告理由。

## 4. Outcome Contract：开发前先锁定用户结果

结果合同控制在一页以内，但必须包含：

```text
目标用户与场景：
当前痛点及证据：
一次任务的最小输入：
可验收交付物：
必须保持不变的事实/资产：
权威依据与适用范围：
已确认假设 / 模型建议：
允许的可逆动作：
禁止动作与末端待交付动作：
正常、失败、越权、证据缺失用例：
领域验收人 / 安全评审人 / 能力 Owner：
停止条件：
```

结果合同不是让普通用户填的表单。需求策展人、能力 Owner 和相关评审人利用原始信号与异步访谈共同完成；普通用户只需确认问题是否被正确理解。

## 5. POC：只消除最大未知，不制造“看起来能用”

一个 POC 最多验证一到两个高风险假设，例如：DOCX 保真差异是否可机械识别、OpenFOAM 字段能否稳定锚定、会议责任项能否在不虚构字段时形成结构化草稿。POC 应预先写出：

- 假设与失败判据；
- approved `source_kind=synthetic` 输入、`fixture_class` 及密级；
- 使用哪些真实 Module/Interface/Seam，哪些仍为 mock；
- 运行次数、证据位置和复现命令；
- 继续、改变方向或停止的决策人。

POC 通过不等于 Phase 0A；旁路 Runtime、手工修结果、挑选成功样例或隐藏失败只能记为探索。若 POC 需要让 Agent 直接访问宿主、绕过 Tool Registry、把普通文件当权威知识或让 AI 判断最终工程结论，应停止并重设边界。

## 6. 构建黄金 tracer bullet

首轮只建设三条完整工作结果：

1. **智能办公助手——技术报告润色与规范化**：DOCX 原件不可变，隔离副本、差异、问题和 Delivery Bundle 完整；
2. **CFD 工程助手——CFD 算例体检**：已有算例只读，发现锚定具体文件/字段，依据、假设和模型建议分开；
3. **会议行动助手——会后纪要与行动项整理**：来源锚定，决策/共识/未决项分离，责任项缺字段集中到末端人工处理。

工程实现采用深 Module 和窄 Interface：控制内核持有普通协作/工作负载身份与资源授权、任务图、策略、队列、审计和交付决定；独立 Safety Identity / PKI / HSM 持有人的安全硬件身份、Safety admission 与 receipt-signing material，Kernel 只消费其可验证结果；OpenClaw/OpenHands 只可作为 `AgentRuntimePort` Adapter，macOS 隔离实现 `SandboxProviderPort`，Office/OpenFOAM 经 `ToolExecutionPort` Adapter 接入；所有动态动作逐次使用 ExecutionTicket。Locality 要求一个 tracer bullet 的合同、manifest、fixtures 和证据引用可以在同一能力工作区内定位。

## 7. FLAi Bench：先证明，再扩大暴露

能力发布包冻结后，通过生产同源执行链跑四轨评测：

1. 确定性回归；
2. 工程质量与具名人工 rubric；
3. 安全治理对抗；
4. 运行效率与已声明的 SLO/预算。

安全、诚实性、依据链和关键回归为不可抵消门。任何必测项 `failed`、`invalid`、`skipped`、`unknown` 或证据不可解析，都不能被平均质量、低 Token 或速度抵消。LLM 评审只提供诊断建议，不能批准金标准、写 `passed` 或签发发布。

每次模型、Prompt、Workflow、Tool/Adapter、Sandbox/Policy、ReleaseKnowledgeBinding 或 rubric 漂移，都重新形成能力发布包。运行时 TaskKnowledgeSnapshot 只要符合 Binding 就绑定该次任务证据，不反向改 release digest。只重跑“容易受影响的几条”必须有版本化影响分析；安全门与关键回归不得口头豁免。

## 8. Phase 0A：5–8 人受控验收

### 开始前

- 冻结参与者、设备环境、数据集、能力版本、任务预算、并发和暴露策略；
- 完成使用说明、已知限制、事故联系人、暂停和恢复演练；
- 为三条 tracer bullet 准备正常、失败、恶意输入和证据缺失任务；
- 确认所有产物清楚标注 real/synthetic/mock/未验证状态。

### 运行中

- 用户提交目标后，自治会话连续工作；不要求其补填 Agent 已能推导的字段；
- 只在末端集中展示无法确认事项、差异、残余风险和 Delivery Bundle；
- 记录取消、超时、并发、恢复、工具失败、模型失败、权限拒绝和 receipt；
- 每个失败进入需求/问题池，并沉淀为 Bench case 或具名说明为何不适合固化。

### 退出

只有机械门、领域验收、安全门、恢复演练和真实状态展示均有证据才可申请 Phase 0B。Phase 0A 报告必须明确写“仅 approved synthetic 受控验收（正常样本 `fixture_class=canonical`），不证明生产就绪”。

## 9. R6：最小真实工作流验证

R6 是 Phase 0A 与 Phase 0B 之间独立的证据门，不是一次“顺手开真实数据”的内部测试。能力 Owner 发起；真实数据 Owner、领域评审人、安全评审人分别签明数据范围、专业质量与安全结论；试点协调人不得代签。

输入只允许 Phase 0A 通过的精确 release、一个获批的最小真实样本/工具路径、单独冻结的 classification、人员、动作和停止条件。输出必须包含真实路径任务、依据与分类传播、准确性 rubric、撤权/回退、支持责任、失败样本和具名结论。任何 Phase 0A synthetic 结果（包括 `fixture_class=canonical`）都不能自动继承；R6 未通过时不得创建 Phase 0B DeploymentBinding。

## 10. Phase 0B：20–30 人限范围业务试点

Phase 0B 不按“平台全功能”开放，而是按精确能力发布包、用户组、项目、数据域、工具和动作逐项放行。至少一条工作流必须使用真实工具和真实数据，完成密级传播、准确性、回退和支持验收。

试点观察五类事实：当前能力、真实使用、质量/安全、资源、组织价值。活跃用户只计算时间窗内真实 user-origin 工作；Token 是资源成本；节时必须有版本化人工基线、有效样本和人工抽样，报告区间与覆盖率。没有基线显示未知，不让模型估算。

扩大人群前必须回答：

- 代表性用户能否独立完成目标；
- 限制和依据是否被理解，而不是被用户绕过；
- 失败能否在预算内停止、恢复并形成可读证据；
- 支持负担是否有具名 Owner 和可持续响应方式；
- 真实收益是否来自可比较样本，而非 Demo 印象。

## 11. 推广：让能力进入工作，而不是追求“安装率”

推广按小批次、同场景展开，唯一日常入口固定为飞书 FLAi 工作空间：

1. 选一类真实任务和一组代表性用户；
2. 用他们自己的可授权样本做情境培训；
3. 演示如何读来源、差异、未知和 Delivery Bundle，而不只演示成功结果；
4. 提供单一反馈入口和清楚的暂停/人工替代路径；
5. 每批次结束后复核质量、安全、支持和价值证据，再决定保持、扩大或缩小。

培训材料必须包含“能做什么、不能做什么、如何识别未验证、谁负责签发、故障时怎么回退”。不得以个人使用次数、Token 或排行榜强迫采用；低采用首先视为产品、流程或信任信号，而非人员态度问题。

## 12. 复盘与共建地图回告

每个试点周期结束形成一页证据复盘：

- 运行的精确能力发布包与暴露范围；
- 完成、失败、取消、退修和安全事件的分开统计；
- 用户反馈及其关联任务，不丢失负面样本；
- Bench 新增/变化和不可抵消门状态；
- 节时或质量价值的基线版本、样本量、区间和覆盖率；
- 已解决的原始需求、仍未解决边界和下一决策；
- 继续、扩大、缩小、暂停、新版本或退役建议。

共建地图位于飞书 FLAi 工作空间，只投影已签路线图、能力发布和上述证据。路线图由人签发，节点状态由事实派生；Bitable 手工编辑不能点绿，也不显示无冻结分母的完成百分比。

## 13. 失败、修订与退役

### 13.1 失败进入资产

每个线上或试点失败必须二选一：固化为 FLAi Bench 回归/对抗 case，或由具名维护者说明为何属于一次性环境、坏数据或不适合固化。修复后创建新能力发布包，旧包和旧失败保持可查。

### 13.2 暂停优先于掩盖

出现越权、泄露、无法强杀、审计断链、关键依据错误或假绿时，先暂停新任务，再调查影响范围。不能切换更宽权限、关闭断言或更换容易通过的评测集维持绿色。

### 13.3 退役条件

以下任一情况可触发退役评审：已有更安全的替代；长期无可证实价值且维护成本高；关键依赖不再可控；风险无法在允许范围内收容；权威流程改变使能力不再适用。退役必须具名签发、停止新入口、回告用户、给出替代/导出路径并保留历史证据。

## 14. 最小运营节奏

- 每周：策展新需求与失败信号，异步补证据；
- 每两周：审查正在孵化的 Outcome Contract、POC 和 Release Manifest；
- 每个候选版本：冻结并运行 FLAi Bench，不按日历跳过门；
- 每个试点批次：复核停止条件、支持负担和扩大范围条件；
- 每月：发布共建地图变更、需求回告、能力证据和风险例外；
- 每季度或重大变更后：复核权威知识、权限/Sandbox、评测包、培训和退役候选。

这些节奏通过飞书工作收件箱、项目空间和具名评审工作包组织，服务于能力和风险，不评价个人产出。会议可以合并，但证据对象、责任与签发不能合并成口头共识；卡片点击或 Bitable 更新只有取得适用的 OwnerCommitReceiptV1 后才构成治理阶段变化。

## 15. 机械验收清单

执行本手册时，一个工作流只有同时满足下列条件才可宣称进入对应阶段：

1. 原始需求、策展事件、路线图签发和 Issue 引用完整且未丢来源；
2. Outcome Contract 有明确用户结果、不可变事实、禁止动作和停止条件；
3. POC 的 mock/synthetic/real 与旁路部分均如实标注；
4. 能力发布包关键成分全部有版本/digest，ReleaseKnowledgeBinding 与外部活态明确，任务时 TaskKnowledgeSnapshot 可证明符合 Binding；
5. FLAi Bench 四轨证据可重建，不可抵消门无 failed/invalid/skipped/unknown；
6. Phase 0A/0B 的人群、数据、工具、动作和有效期与签发范围精确匹配；
7. 发布、扩大、暂停、恢复和退役均由具名授权人签发，AI 无写权限；
8. 用户反馈能回链 release/task，并收到采纳、暂缓、不采纳或发布边界的回告；
9. 指标包含定义版本、时间窗、样本量和 unknown/null/zero 语义；
10. 任何个人 Token、任务量或采用率都未被输出为绩效排名；团队指标的 purpose、最小聚合、下钻职责、保留期和导出限制均有版本化策略与越权负例。
11. 日常用户只需进入飞书 FLAi 工作空间；GitHub/FLAi/Knowledge/Audit/Secret 的来源事实仍保持唯一 owner 且可回查。
12. 高影响动作有精确 PreparedCommand/ReviewChallengeV1、commit-time 重验和
    OwnerCommitReceiptV1；receipt invalid、EffectUnknownV1 或 stale projection 均不能推进阶段。
13. 飞书不可用时新的正常管理暂停，但 FLAi 的 kill/revoke/isolate/credential invalidation 安全生存通道可用且不能用于正常发布。

## 16. 本阶段非目标

- `OUT-OF-SCOPE`：一次建设完整 Office 全家桶、全自主 CFD、实时会议伴随或 Agent 市场；
- `OUT-OF-SCOPE`：立即导入真实敏感知识或开放真实不可逆外部动作；
- `OUT-OF-SCOPE`：用 AI 替代路线图、领域、安全、发布或工程签发；
- `OUT-OF-SCOPE`：把月度 Demo、用户数量或 Token 消耗当作转型成功结论；
- `OUT-OF-SCOPE`：在本设计阶段修改现有 API、数据模型、角色枚举或运行状态机。
